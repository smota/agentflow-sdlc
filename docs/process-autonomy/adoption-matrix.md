# Adoption documentation coverage matrix — S8

This matrix describes the documented product entrypoints for the five adoption journeys in the
process-autonomy plan. It is an operator guide, not evidence that an end-to-end journey has been
qualified. Use the packaged `agentflow-sdlc` commands in [assisted onboarding](../assisted-onboarding.md)
and [run operations](../run-operations.md); internal APIs and proposed interfaces are not CLI commands.

catalogued `SKILL.md`; package parity compares their bytes. The obsolete coordinator name is not
a supported installation target. Installed runtime links remain outside these source checks.

For journey 4, reuse [public delivery qualification](live-delivery-qualification.md) for the

limitations remain binding; it is not a clean-context adoption proof.
For journey 5, configure [optional observability](observability.md) for process telemetry.
The generic host ports in the table are separate from this implemented optional adapter.
A verified engineering result never accepts an SDLC gate or applies a commit automatically.

Issue #304 qualifies the five journeys above from packaged entrypoints. Existing/partial setup
includes shared skills; old/unknown setup includes separate update deferral and selective recovery.

as a fresh cold-reader pass; broad model/host qualification and efficiency targets are excluded.

## Documentation integrity rules

1. **Source and installation stay separate.** Development-version checks use this checkout's source. Do not edit installed runtime links or imply source edits redeploy an installation.
2. **Authority follows implemented entrypoints.** A CLI example must match the packaged command contract. Library functions, proposals and fixtures are not user-facing commands or qualification evidence.
3. **Approval and ceilings are bounded claims.** A reviewed run contract is not a universal approve-once delegation grant. Budget enforcement depends on a host that can verify usage in the configured unit; currency/token ceilings remain unsupported until enforcing adapters qualify.
4. **Readiness stays distinct.** Project adoption, runtime capability evidence and readiness of a governed change are separate. A passing setup check or digest does not prove tests, acceptance, publication or independent human review.
5. **Recovery is receipt-backed and scoped.** Use the exact plan/receipt and documented recovery command. Never recommend `git clean`, broad deletion, or lock removal as an adoption rollback.
6. **Optional integrations remain optional.** Name the integration and supported capability explicitly; absence is not evidence of successful fallback or a qualified alternate path.
