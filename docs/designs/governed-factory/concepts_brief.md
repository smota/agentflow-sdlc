## Overview

AgentFlow is an open-source governance layer for AI coding agents. This brief covers a six-month evolution of it into a governed factory that runs without a human present between human-set boundaries. Agents build it through AgentFlow itself. The author's time is not a scheduler input: he audits, sets policy and handles exceptions when he chooses, and can pause and resume the factory coordinator at any time (D21). Agents merge their own work.

**Month-6 claim:** the named reference stack works end to end and is in actual use. It is used by the factory building itself and on the author's own repositories. Outside use is welcome but is not a gate. The supporting evidence is a published conformance report showing two implementations passing each port's suite.

**Month-6 package** (supports an implementation-and-services offer): an npm release, a mock-GxP sample repository, an offline command that verifies signed evidence, a case study of AgentFlow building itself, a claims ledger, technical documentation, manuals and a product website.

**Positioning hypothesis (not settled):** a governance and evidence layer for agentic delivery that plugs into rented engines through ports and ships one fully working reference stack. "Integrator" describes the method, not the headline. No prospect has asked for any named tool, and the author is still looking for the right positioning. The offer one-pager (author-owned) is where the hypothesis gets tested.

**GxP position:** lightweight. The factory maps its recorded evidence to Part 11, Annex 11 and GAMP clauses. Wording is "supports" and "maps to", never "compliant" or "validated". No external validation and no certificate.

Fixed assumptions: Windows 11 plus WSL; Claude and Agy (Gemini) as vendors; GitHub as the only source system; subscription CLIs only; no competing fork of other projects; rent infrastructure wherever it fits.

## Analysis

**Verified state of AgentFlow today** (audit 2026-11-22; items marked "checked" were re-verified in code during review):

- Six control modules the guiding principles cite as enforcement have no product importer outside tests: `lib/audit/role-flow-span.mjs`, `lib/gates/gate-sweeper.mjs`, `lib/qa/process-supervisor.mjs`, `lib/qa/qa-contract-verifier.mjs`, `lib/runtime/handover-protocol.mjs`, `lib/runtime/lease-fencing.mjs` (checked). A working digest-chained event store exists in `lib/core/run-state.mjs` (`previousDigest`, `generation`, compare-and-swap on `refs/heads/agentflow-state`). It is unsigned with self-asserted time. `lease-fencing` duplicates `seat-lease.mjs`.
- Agents are not isolated. `lib/providers/local-cli.mjs` is a one-shot `spawnSync` runner with a 120 s timeout, no cancel, and passes `HOME` and `USERPROFILE` through (checked). A `gh auth token` fallback exists (`lib/sources/github-credential.mjs:13`, checked). No kill switch exists. There is no per-day budget. No unattended loop launches agent work.
- Gates accept self-asserted JSON (`lib/core/gate.mjs:101-124`), and `human` is a registry slug.
- The four-eyes model-family check (`lib/core/execution-receipt.mjs:203-205`) runs only when `metadata.builderReceipt` is set. Nothing sets it. The `claude-cli` and `agy-cli` registry entries have no `modelFlag`. The Gemini route in `lib/config/execution-distribution.mjs:15` still goes through the removed `pi` (checked).

- The only hardened write path is for Codex (`lib/providers/codex-engineering.mjs`: `--ephemeral`, `--ignore-user-config`, `--sandbox`, workspace snapshots). Claude and Agy need equivalents.
- The v1.9.0 self-improvement pipeline is script-only (checked). It proposes edits to path-ownership, permissions and `SKILL.md` from agent-writable traces.
- `scripts/audit-reachability.mjs` scans only `lib/core/` and `lib/verification/`, so the unwired modules passed CI.
- GxP content: none in the repo. Receipts lack signer identity, signature meaning and reason for change. Two digest conventions coexist (`provider-receipt.mjs:5` unordered, `record-digest.mjs:3-18` canonical). The last 50 merged PRs had a median of 792 changed lines, and 15 of 50 were over 1,500.
- Strong assets to keep: stale-digest review attestation, oracle custody with revocation epochs, the four-eyes check (once wired), the human-gate rule, fail-closed budget admission, distribution pinning with confirm-token migrations, risk-adaptive posture, the three-OS release gate.

**What shaped this plan**

1. Human attention is not a scheduler input (D21). Under agent merge the author audits samples, sets policy and handles exceptions when he chooses. Throughput is limited by the in-flight cap, the revert circuit breaker and subscription quota, and a dead-man pause stops an unattended factory that nobody has checked on.
2. The agents build their own safety layer, so a containment floor comes first, built from rented controls.
3. Claims exceeded code, so claim truth is a standing CI rule from week 1.
4. Self-asserted gates mean a minimal slice of signing (signed approvals, trusted writers) must precede the first unattended run.
5. GxP fields shape the evidence schema, so the envelope is designed in weeks 1-3 with a hand-written golden fixture of the final outputs.
6. A services offer is sold on a demonstrable package, so the walking skeleton works from weeks 6-8 and measurement starts in week 1.
7. Landscape result: popular frameworks are light prompt packs with no enforcement. Engines enforce but none signs approvals or targets GxP. The governed and regulated niche is open (secondary sources, not tested by the author).

**Corrections made during review:** the hash chain is partly present (`run-state.mjs`), so only `role-flow-span` is unwired. Per-day budget and kill switch are absent. Several recommendations changed when the author chose Claude and Agy over Codex.

## Design requirements

**Box and verifier** (make unconditional agent merge recoverable)

1. **The box lives outside the repo.** Agents can merge any repository change but cannot change the constraints around them. Those are account-level settings an agent token cannot edit: GitHub rulesets and branch protection, the merge identity's permissions, vendor quotas, kill-switch authority, signing keys, npm trusted-publishing configuration. A human sets them once.
2. **The verifier that judges a change is not the change.** Required checks run a pinned, digest-identified verifier from the last release, not code from the PR branch ("release N-1 governs release N").
3. **Every merge needs an independent cross-family review**, a digest-bound attestation. The required check fails if it is stale or missing.
4. **Merge queue with post-merge verification and automatic revert.** The merge identity is a narrow-permission GitHub App used only through the queue. The full suite and the red-team suite run after merge, and a failure reverts. A circuit breaker pauses merging after N reverts in a window (N to calibrate) and engages the kill switch.
5. **Time-lock on `factory-core` changes.** A fixed window (for example 24 hours, to calibrate) in which the author can veto. Silence is consent, so it never stalls the factory.
6. **The red-team canon is held outside the repo with a ratchet.** The canon only grows, and a PR that removes or loosens a case fails a check that reads the external canon. It runs on every `factory-core` change and in post-merge verification. Seeded defects, holdouts and the verifier digest are held the same way.
7. **Release uses credentialless publishing.** npm trusted publishing is configured once by the author. Agents hold no publish credential.

**Coordinator and steward** (D20, D21)

- The coordinator plans, dispatches, merges and pauses. It is the steering-plane seat `steer.lead` run as an agent with the existing `agentflow-steerer` skill. It is invoked per event or schedule in a fresh, stateless session that reads durable state (issues, milestones, goals, receipts) and acts, like the existing stateless actuator `scripts/actuate-readiness.mjs`. It is never the builder's or reviewer's session, and it runs out of the rig.
- **Authority is delegated, not impersonated.** A delegation record signed by the author and stored outside the repo lists scope (repositories, branches, risk classes), allowed actions (merge, hold, dispatch, pause), and an expiry. The steward acts through its own GitHub App identity, not the author's personal GitHub login, so the record shows "steward acting under delegation D-n" and not "Samuel". Revocation is removing the App installation or setting the pause flag.
- **Its authority is one-directional.** The deterministic evaluator (`lib/core/steering-merge-policy.mjs`) and the required checks decide what may merge. The steward may hold, escalate or release what the evaluator allows, and may never override it. Issue, PR and comment text reaches it as data. A prompt that talks the steward into merging something the evaluator held does nothing, because the evaluator output is the gate.
- Every merge records the delegation ID, the evaluator result, the review attestation digest and the queue run.
- **States:** running; draining (no new admissions, in-flight items finish or checkpoint); paused; killed (hard stop through the persisted flag). Pause is graceful and resume is one command. Resume re-reads the durable plan and reconciles with receipts, and must be idempotent: pausing mid-run and resuming produces the same evidence chain with no duplicates. This builds on the existing `handoff` and `resume` commands (which route to `run-delivery`) and is proven by a conformance case.
- While paused, nothing merges. A pending time-lock stays pending, and the author can still veto. Pauses and host downtime interrupt soaks, so a soak counts active hours (see the M2 exit).
- Agreed default: a dead-man pause after N days without a human check-in (N=7, changeable or disabled by the author).
  **Substrate and receipts** 8. A substrate contract with operations: provision, launch, observe, cancel, destroy, reconcile. It states the credential, filesystem, network and resource boundaries. Controls sit outside the substrate (for the reference substrate, `sbx` supplies the egress policy, proxy and audit log, and the sandbox holds no GitHub credential: the launcher pushes the result with the builder App) so any substrate is replaceable. 9. A conformance suite built from the red-team events: reading `~/.ssh` or gh config, ambient tokens, pushing to a protected branch, a non-allowlisted host, writing outside the worktree, overrunning time or budget, cancellation, restart reconciliation, cleanup, and a candidate that edits its own verifier. A deliberately weak adapter must fail it. Today's `local-cli` is expected to fail at least six cases. 10. Receipts record actual model, image or substrate identity, egress-policy digest and kill result. The evidence envelope carries optional `substrate` and `evaluator` blocks, present but null until used. Adding them after signing would break signed history.

**Learning boundary** (applies to the wired v1.9.0 pipeline and to any later learner) 11. Learning is change control for agent configuration. It is a worker role whose output is an ordinary PR through the same pinned verifier, cross-family review and time-lock. It gets no privileged path. 12. Evaluators, verifier source, reviewer and judge prompts, thresholds and holdouts are never learner outputs and sit outside the learner's write scope. 13. Reward comes from lagged post-merge outcomes (reverts, escapes, red-team results), never from merge rate or reviewer approval. 14. Signals are untrusted input. The pipeline's current input (`.agent-runs/*.jsonl`) is agent-writable, so lessons are sanitized, credential-free and never auto-applied. 15. Promotion needs a gain above run-to-run noise, a canary lane, digest-pinned versioned artifacts and automatic rollback. Reverts attributed to a learned artifact trip the circuit breaker. A run is governed by the artifact version recorded at its start. 16. The learner has its own identity and an idle-only quota lane so it cannot starve builds. External optimizers start only after L3 is proven and enough scored outcomes exist.

**Defaults applied for D16** (the author asked what these mean)

- `factory-core` means the files whose change could weaken the factory's own safety: gates, attestations, custody, receipts, policy, validators, hooks, workflows, the signer and verifier, the pinned verifier, reviewer and judge prompts, the `claude-agy` profile and model-routing config. Changes there wait the time-lock and need a different-family review.
- Builder prompts, skills, playbooks and lessons are an "agent-configuration" class. They use the normal merge path (cross-family review, post-merge verification, revert), and the red-team canon includes a case where a learned instruction says to skip review or touch protected paths.
- The confirm token is the typed digest the CLI requires to apply a policy or profile change. Under agent merge an agent could supply it, so it stops accidents, not adversaries. Protection against an adversarial change comes from the box (requirement 1), the time-lock and the external canon, not from the token.

**Integration admission rule.** An integration is admitted only if it deletes a plan item or is the only way to meet an exit criterion. One non-default adapter per port and at most one new external dependency per milestone, each with a retirement test, a supplier-table row and a digest pin. Adapters live out of process in `adapters/<name>/`. Nothing in the verifier, the offline `evidence verify` or the published core package imports them. No document may say "supports X" without an `implemented` ledger row linked to a passing conformance run.

### Week-0 account-level acts (human, once)

The box lives outside the repo (requirement 1), so these acts stay with the author. Nothing in the factory, and no agent session, holds the credentials or authority to perform them. Agents prepare the instructions, templates and a read-only checker script that verifies each one is in place. The checker is part of the week-0 exit criteria.

1. Create and install the GitHub Apps: a builder identity (branches and PRs, no merge right), a reviewer identity (review attestations only), and the steward's merge identity (queue only, no code authorship, no admin).
2. Sign the delegation record with the author's key, kept outside the sandbox. A delegation signed by an agent would defeat its purpose.
3. Set rulesets, branch protection, CODEOWNERS and the required checks on each repository the factory touches.
4. Configure npm trusted publishing, bound to the release workflow.
5. Set the kill-switch authority and the run-count and quota caps.
6. Set the host rules from "Standing rules" (sleep and hibernation, Windows update restart policy, `sbx` pin and updates, watchdog; WSL2 idle shutdown only if the fallback substrate is in use).

Everything else in the plan is autonomous: code, tests, ADR drafts, the delegation record format, the steward skill and configuration, the conformance suite, documentation and the website.

## Alternatives Weighed

- **Original six-phase roadmap.** Rejected by author review: sized for a team, wrong order for evidence and GxP.
- **Build the execution engine in-house.** Rejected by author review: beyond the review budget. Rent isolation (`sbx`) and build only a thin launcher. OpenRig is an optional adapter, trimmed to the minimal scenario (D27).
- **Hosted sandbox for subscription agents (Celesto, GitHub-hosted runners).** Rejected by author (D2): subscription credentials stay on author-controlled machines.
- **ADK as agent runtime or eval authority.** Rejected by council and reviewers: it calls models through APIs against subscription-only billing, duplicates AgentFlow's phase graph, and sees only a wrapper around the CLI workers.
- **Self-improvement frameworks at runtime (DGM, SEAL, ADAS).** Rejected: they rewrite code, weights or evaluators, and the dossier shows a case of faked tool use.
- **Wire every unwired module.** Rejected as the default. Retract fencing, the 15% cap, WIP checkpoint branches and the `role-flow-span` chain. The sweeper and supervisor are wired after adaptation (D17).
- **Custom hash chain, OPA/Cedar and a full in-toto layer.** Rejected: too much for one maintainer. Use signed commits, GitHub attestations and an RFC 3161 timestamp.
- **Human merge as the end state ("Samuel merges").** Superseded by the author (D4). Kept only for the early rungs of the ladder.
- **"Governed integrator" as the headline.** Not adopted by council and reviewers: integrators inherit every dependency's risk and rarely own a category. Kept as a hypothesis for positioning (D1).
- **GxP last.** Rejected: its fields shape the evidence schema.
- **Dogfood only on AgentFlow's repo.** Rejected: add the mock-GxP repo as a second consumer.

## Key Decisions & Staging for Next Steps

**Standing rules from week 1**

- Four contracts frozen early: C1 claims ledger, C2 trust boundary (what an agent can read, write, spend and call), C3 evidence envelope, C4 requirement-ID spine.
- Instrumentation from day 1: PRs, scope drift, review and audit effort, rework, reverts and escapes, spend, containment events, gate wait time, failure-class tags. Add observation kinds for sandbox lifecycle, egress denial, kill switch, merge, revert, circuit-breaker trip and learning proposal (the current vocabulary drops unknown kinds). Add a run-level correlation ID and a redacted, size-capped transcript per run.
- Surface freeze: no new schema, validator or subcommand without retiring one or stating why. No library code merges without a reachable non-test caller and a CLI-level test (a conformance suite counts as a caller for a second implementation).
- Back-pressure: stop starting work in a lane that has 3 PRs in flight, or after a revert circuit-breaker trip.
- Audit cadence is the author's choice. The coordinator reports audit backlog and, by the agreed default, pauses itself after N days without a human check-in (N=7, changeable or disabled by the author). PR scope (D11) keeps each change auditable.
- Unattended agent runs execute in `sbx` microVMs on the author's own always-on Windows machine (D18, D23). The launcher, steward and coordinator run on the host, and the WSL2 stack is the fallback substrate. So: disable sleep and hibernation; set the Windows update restart policy so it does not interrupt a soak; pin `sbx` at 0.51.0 or later and review its updates; keep WSL2 from idle shutdown when the fallback is in use; run a watchdog that alerts when the host, `sbx` or the coordinator stops; and keep the pause flag and token revocation reachable when the host is down (they are account-level, requirement 1). The host is a single point of failure, and the case study reports its downtime.
- Each milestone is a goal that the author admits through the existing admission person gate (D32).
