# Execution plan: observable, efficient and delegated AgentFlow

Status: final planning proposal after three council rounds; conditional findings dispositioned by Codex below. Approved for execution by the maintainer in the active session on 2026-09-25; implementation and verification in progress, not yet delivered.
Date: 2026-09-25. Planning method: installed TechLead Planner, Clean Architecture and Writing for Agents. Follow-up source: retrospective #259; prior implementation #249/#258 is complete, not reopened.

## Goal and acceptance

Make AgentFlow the portable SDLC process owner: intent, scope, authority, handovers, evidence, acceptance and delivery state. Reduce coordination and context cost without weakening recovery. Add OpenTelemetry and a simple explicit delegation to execute an approved plan to a ready PR or a named merge. Keep technical execution replaceable, including a minimal direct executor and optional Meshloop.

Acceptance: (A1) one coherent authoritative run matches actual executed transitions; (A2) explicit delegated authority authorizes only approved scope/actions and never impersonates human candidate review; (A3) fresh-instance continuation reconstructs the correct state without this chat; (A4) measured source/context cost decreases without dropping mandatory barriers; (A5) OTel export, disabled mode and offline mode preserve identical workflow decisions; (A6) direct and Meshloop paths pass the same process-boundary conformance suite, and each product operates independently through a versioned optional engineering interface; (A7) a fault-injected pilot proves no duplicate external effects and no new action admission after acknowledged revocation; (A8) all source, policy, schema, documentation and package changes ship consistently; (A9) a fresh adopter and a fresh agent can complete supported adoption and continuation journeys from published entry points without this conversation or undocumented maintainer guidance.

## Architecture decisions

Keep ADR004/005 boundaries and existing SourceAdapter, CollaborationIntent, ProviderBinding, ExecutionReceipt, ArtifactRef and reducer. Extend, do not create a parallel orchestration kernel.

Three ADR proposals accompany S0, become accepted only through the workstream's policy: (D1) delegation origin/assurance and admitted-action race semantics; (D2) versioned persistence and portable continuation; (D3) execution-provider and observability boundaries. A separate amendment defines compact execution records and permitted phase composition without inventing performed work.

The authoritative ledger is the only source of workflow state. Local cache and continuation summaries are derived. GitHub issue/PR comments are human projections, updated on substantive changes. Telemetry is a separate, optional side channel; it never grants or certifies acceptance.

No mandatory DAG or model roster in the core. One SDLC phase may contain several execution attempts and technical tasks. Role responsibilities remain; the approved workflow selects which phases are required and records justified skips. Batching records cannot skip authorization or acceptance barriers.

## Delegation contract and user experience

User-facing choices: approve the displayed plan and execute to ready PR; or approve and execute through merge into the named base. The approval summary displays scope, destination, review policy, budgets, expiration and stop conditions. No second confirmation for an action already inside a valid grant; actual policy-required human candidate review remains visibly separate.

A host-resolved grant binds issuer origin/assurance, delegate and allowed narrower subdelegation, plan digest, policy digest, repository/base, permitted paths/capabilities/action set, checks and review rules, limits, expiry and authoritative revocation reference. Config selects trusted issuers; a config value, GitHub comment written by the agent using shared credentials, arbitrary actor string or hash is NOT identity proof. Existing authorize callback returns a boolean today; it does not already emit grants. Add typed issue/resolve delegation use cases at the same boundary, preserving boolean authorization compatibility, and have the admission callback consume the independently resolved grant. No signature scheme or identity service is required. The authority adapter verifies stored origin/revision at its declared assurance level. Legacy boolean-true authorization remains compatible for existing callers but is insufficient at delegated admission: only a typed issue/resolve decision supplies the grant. The host approval adapter records an explicit user action using its supported authentication boundary. No signed-by-human assertion is manufactured.

Provide an explicitly labeled local-cooperative operator mode and a trusted-host mode. A local approval command under a shared OS account cannot distinguish malicious same-user agents; policy may reject that assurance for protected actions. The initial feasibility spike must demonstrate one real approval surface and replay/forgery rejection under its stated threat model. If the current host cannot export a verifiable user decision, retain ready-PR and report through-merge unsupported for that binding; do not silently claim R4 delivered. Full through-merge acceptance requires a working trusted binding or explicitly policy-authorized cooperative mode disclosed in approval.

Plan digest stays fixed. Candidate code evolves only to implement that plan, within approved scope, action set and assertions. Each technical review/check binds the exact candidate. The stored grant policy decides materiality of scope, assertions, policy, protected paths, action set and budget. Such changes invalidate or re-evaluate the grant before the next admission; ordinary implementation edits admitted by that predicate do not require plan reapproval. No retroactive grants for the old run.

S2 must deliver an authoritative admission transaction that conditionally commits grant revision/revocation epoch and writer/run revision together before S3 enables external actions. An adapter unable to provide that capability cannot claim revocation-safe autonomous actions. The GitHub design uses its existing isolated Git ref, not issue-comment read/write as a lock: construct one single-parent commit containing both admission and authority expectations, parented at the observed ref, then request a non-force ref update. Under the documented single-parent cooperative writer protocol, concurrent divergent commits cannot both fast-forward. This is the conditional append mechanism to prove; a confirmation read alone is NOT a transaction. S2/S3 must demonstrate conflicting admissions/revocations, failed updates and ambiguous confirmation with no action dispatched before acknowledged admission. External administrators rewriting refs and hostile shared credentials remain outside the assurance claim; if the provider cannot prove the capability, that binding stays unavailable for through-merge. Admission is the linearization boundary: re-resolve grant/expiry/revocation and atomically reserve the business operation against writer/run revision before an external action. A previously admitted operation may finish after revocation; attempt cancellation only with supported capability, then reconcile. Acknowledged revocation blocks new admissions. A local admission check cannot revoke arbitrary external processes; no exactly-once guarantee for providers lacking idempotency or authoritative outcome lookup.

Budgets separate control-plane persistence from business effects. Proposed per night:8h execution window,2 attempts at the selected tier plus1 bounded escalation per task, and explicit plan-derived external-effect allowance. Exhausted work or external-effect budget denies every new business effect, while a pre-reserved bounded checkpoint/reconciliation budget remains available only to safety operations and cannot be expanded or consumed by the candidate. S3 cannot ship budgeted autonomy until exhaustion tests prove this. If authority storage remains unavailable after bounded reconciliation, record a local pending/unknown checkpoint and prohibit new business effects. Telemetry flush is best effort and cannot block the safety checkpoint. A hard token/currency ceiling requires a named provider with independently probed enforcement at issuance; unknown or incapable providers and hard ceilings with deferred provider selection are rejected. Revalidate provider identity/capability at admission; a fallback must satisfy the same envelope or stop. Deferred providers may use advisory limits, or admission-enforced limits only after actual usage becomes observable, never a guaranteed in-flight cap. Observed usage alone supports admission limits and post-fact reporting, not guaranteed in-flight ceilings. Otherwise expose unknown/advisory or admission-enforced fidelity explicitly. Do not switch to paid APIs or another principal silently.

## Telemetry and analytics

Instrument source HTTP, request/response bytes, physical file reads, context bytes admitted, dispatch/attempt, role validation, acceptance, recovery, pause, waiting and delivery. Export traces/metrics via OTel adapter and OTLP; use an in-memory receiver for tests and bounded local storage for disconnected sessions. Pin SDK and semantic conventions. Domain emits typed plain observations, not SDK types.

Correlate run_id, session_id, attempt_id, operation_id, parent/linked spans, candidate/plan/policy/grant digests and schema version. Long runs use per-session/attempt traces linked by durable run identity. IDs belong to traces/events, not unbounded metric labels. Native harness internals are observed only when exposed by supported hooks/usage outputs; missing coverage remains partial/unknown. Token counts are numeric allowlisted usage, distinct from secret tokens.

Typed attribute allowlist; no source, prompts, transcripts, credentials, absolute private paths or full commands by default. Destination is off until configured; no collector installation required. Proposed telemetry bounds:8MiB telemetry-buffer memory,32MiB local spool,7-day local retention,2s shutdown flush; report losses/coverage and use bounded retry/backoff. Mandatory audit records occupy the authoritative source and a separate bounded pending-audit journal; they never enter the 32MiB telemetry spool. Proposed pending-audit capacity is8MiB plus a preallocated64KiB stop-record reserve; source acknowledgment/reconciliation permits journal compaction, not elapsed-time deletion of unacknowledged evidence. Admission reserves space for required intent/outcome/stop records before work. If audit capacity is insufficient or source cannot accept required records, refuse new business effects, checkpoint with the reserved slot and report pending/unknown. This pending journal remains local and non-authoritative until source acknowledgment; it is not disaster backup. Retain acknowledged audit history under project source policy. Tests distinguish telemetry eviction from audit-full admission failure.

First analysis export answers: source calls and bytes per accepted delivery/checkpoint; repeated context ratio; observed cache/token usage; dispatch/rework counts; time in execution, coordination, human wait and CI; time to first verified evidence; cold/warm resume latency; rejected/expired/revoked grants; recovery fidelity and duplicate effects. Report denominators, workload, runtime versions, unknowns and estimates. No dashboard or financial-cost claims from missing provider data.
